## Требования к исходному коду
Редакция: **2026-09-24** (адаптировано под проект)

### Основные положения

- По возможности пишите самодокументируемый код [link](https://habr.com/ru/post/458264/)
- При именовании объектов придерживайтесь английского языка и подбора корректных доменных терминов
- При проектировании классов придерживайтесь принципов SOLID (https://en.wikipedia.org/wiki/SOLID), а также по возможности классическими принципами `KISS`, `DRY` и `YAGNI`
- При проектировании архитектуры решения придерживайтесь принципов чистой архитектуры (https://github.com/jasontaylordev/CleanArchitecture)

### Форматирование кода Python
- Наименование каталогов должно соответствовать [`CamelCase`](https://ru.wikipedia.org/wiki/%D0%92%D0%B5%D1%80%D0%B1%D0%BB%D1%8E%D0%B6%D0%B8%D0%B9_%D1%80%D0%B5%D0%B3%D0%B8%D1%81%D1%82%D1%80)
- Наименование классов должно соответствовать `CapWords` (по [PEP 8](https://peps.python.org/pep-0008/#class-names))
- Наименование свойств, методов, функций, переменных и файлов должно соответствовать `lowercase_separated_by_underscores`

- **Обязательно** наличие docstring для каждого класса, метода и свойства
- Docstring пишется на русском языке в формате reST: `:param имя:`, `:return:`, `:raises ИмяИсключения:`
- В `:raises` указывается исключение, которое код действительно выбрасывает

### Тестирование

При написании тестов четко разделяйте их по типам: `юнит-тесты`, `интеграционные тесты`, `функциональные тесты / e2e`. 
Используйте TDD или отладку с помощью юнит-тестов только для тех блоков, которым не свойственно частое изменение или модификация. 
Перед написанием тестов руководствуйтесь здравым смыслом и не забывайте, что тесты - это тоже код, который требует поддержки и актуализации.

- Используем рекомендации [Microsoft](https://learn.microsoft.com/ru-ru/dotnet/core/testing/unit-testing-best-practices)
- Именуем тесты следующим образом: **test_НаименованиеМетодаИлиСвойства_Условие_ОжидаемыйРезультат**, где каждая часть записывается на английском в `lowercase_separated_by_underscores`, например `test_name_setter_empty_string_raises`
- **Обязательно** наличие docstring для каждого теста с подробным описанием сценария
- Тело теста делится на три части, каждая помечена комментарием:
    - `# Подготовка` - создание объектов и исходных данных
    - `# Действие` - вызов проверяемого метода или свойства
    - `# Проверка` - сравнение результата с ожидаемым
- Если действие и проверка неразделимы (например, проверка исключения через `pytest.raises`), используется общий комментарий `# Действие и проверка`
- В параметризованных тестах исходные данные задаются в `@pytest.mark.parametrize`, поэтому над декоратором ставится комментарий `# Подготовка`. Он нужен и тогда, когда в теле теста есть своя подготовка
